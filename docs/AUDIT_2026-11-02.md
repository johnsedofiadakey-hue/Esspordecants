# Esspor audit and build-out list (2026-11-02)

Scope: the customer journey, the admin portal, the API, cost, security and operations, as they are in the repository today. Each item says how it was checked. "Not checked" means it was read in code only.

## 1. Verdict

The storefront, API and admin work together locally from catalogue to placed order. It is not ready to take real orders. The blockers are business decisions (payment, delivery, real products and photos) and four missing pieces that every order depends on: **order alerts, customer order tracking, bot protection and legal pages**.

## 2. How it was checked

- API: `npm test` against the Firebase emulators, 25 of 25 passing, plus typechecks and production builds for all three apps.
- Storefront: headless Chrome against a production build and the emulators, desktop and 390 px wide, across ten routes (page weight, titles, metadata, broken images, overflow, console errors), and a full order (product, bag, pickup or delivery, confirmation).
- Admin: signed in to the local admin in the browser pane. Checked the overview, the product editor (new Photos and videos card) and an order's detail screen. Content, Settings and the team screens were not opened by eye.
- Not checked: anything on the live Firebase project (no owner account exists there yet), real video playback, real payment, email or SMS.

## 3. Customer journey (walked end to end)

Home or Shop, then Product, then **Bag and checkout (one page)**, then Confirmation. Two clicks to reach the form from a product. The form asks for full name and phone, plus an address for delivery only.

What works: the announcement bar, gallery with photos and videos, server-priced bag, pickup or delivery with the fee added, validation, confirmation with the order number, no horizontal scroll at 390 px (after the fix below).

Found and fixed during this audit: the product page was wider than a phone screen once a product had four or more media items. The thumbnail row now scrolls.

## 4. Admin portal

Works (checked in the browser or by tests): sign-in, overview, product list and editor, uploads with approval, size variants, publish gates, orders list and detail, status changes with timeline and stock restore, delivery options with pickup or delivery type, team management, audit log.

Missing for day-to-day running:

| # | Gap |
|---|---|
| A1 | **No alert when an order arrives.** Someone has to keep the orders screen open. |
| A2 | No bulk product import (CSV or spreadsheet). Entering a catalogue of Arabian, designer and niche scents one form at a time will be slow. |
| A3 | No "message the customer" shortcut (WhatsApp link with the order number filled in), and no courier or tracking-note field on an order. |
| A4 | No order export, pick or packing list, or label printout. |
| A5 | No discount codes, customers list, or sales reports. Decide whether they are needed at launch. |
| A6 | Photos shown to buyers depend on admin discipline: nothing stops an unapproved placeholder from looking real except the checklist. This is by design, but a short admin guide is missing. |
| A7 | Admin screens for Content and Settings, and a real video preview, were not checked by eye. |

## 5. Cost and performance

Done this session (details in `docs/CLAUDE_REPORT.md`, section 10): photo shrinking before upload, tighter limits, concept images from 3.4 MB to 116 KB, lazy loading, videos load only when played, day-long media caching, one Firestore read per media request, a 30 second catalogue cache.

Measured with the production build and no compression (real Hosting serves gzip): home page 484 KB, other pages about 362 KB. JavaScript is 249 KB raw, about 78 KB gzipped.

Open:

| # | Item |
|---|---|
| C1 | No billing budget or alert exists. Create one (command in the report). It alerts only; it does not cap spend. |
| C2 | Video seeking reaches the function (range responses are not cached by the CDN). Fine for a few short clips. Revisit if video becomes a feature. |
| C3 | No rate limiting on any public route, so one bot could run up function time. `maxInstances: 10` is the ceiling. |
| C4 | Admin list screens read whole collections (orders up to 1000 reads when searching). Fine at launch volume. |

## 6. Security and abuse

Good: Firestore and Storage deny all client access; admin tokens are checked with revocation; roles are enforced server-side; uploads are checked by content; prices and stock are server-authoritative; checkout is closed by default; the admin site sends no-index and frame-deny headers; the browser API key is restricted.

| # | Item |
|---|---|
| S1 | **Bot and spam protection on `POST /api/v1/orders` and the quote route.** Phone-only orders are easy to fake and each fake reserves stock. Add a challenge (for example Cloudflare Turnstile or App Check), a per-phone and per-IP limit, and an admin "release stock" habit. |
| S2 | No Content Security Policy on either site. |
| S3 | `npm audit` reports 6 moderate issues in the API's dependencies (`glob` and `minimatch`, build and tooling chain). No fix is urgent, but the next dependency update should clear them. Storefront and admin report none. |
| S4 | Phone numbers and addresses are personal data. See O3. |
| S5 | The live owner account has not been created, and the signed-in live admin has never been used. |

## 7. Search, sharing and polish

Checked on every route: no broken images, no console errors, one heading per page, alt text on all images.

| # | Gap |
|---|---|
| P1 | Every page has the same title. No canonical link, social preview tags or favicon. |
| P2 | The site is a client-rendered app, so link previews (WhatsApp, Instagram) and search engines see an empty shell for product pages. Fixing it means serving meta tags for `/product/:slug` from a small function, or prerendering. |
| P3 | Unknown URLs show "Page not found" but return HTTP 200 (soft 404). |
| P4 | No sitemap or robots file. |
| P5 | `/preview/product` is public and indexable; remove or no-index it before launch. |
| P6 | Generated concept imagery and its "concept" captions remain on the home page until real photography replaces it. |
| P7 | Accessibility was not audited in depth. Known: videos have a description but no captions; orange-on-cream text contrast needs a check. |
| P8 | The announcement CMS slot (`announcement`) exists but the bar is fixed text; making it editable costs an extra API call per page, so bake it at build or fetch once. |

## 8. Operations

| # | Item |
|---|---|
| O1 | No error or uptime alerts (for example on function 5xx errors) and no uptime check. |
| O2 | No Firestore backup plan (scheduled export or point-in-time recovery). Orders are the data that cannot be recreated. |
| O3 | No privacy policy, terms, delivery and returns pages. Collecting phone numbers and addresses in Ghana likely needs registration with the Data Protection Commission; check with a lawyer. |
| O4 | No custom domain; the site lives at `esspordecants.web.app`. |
| O5 | No tests for the storefront or admin, and CI runs only the API tests. The headless scripts used in this audit could become automated browser tests. |
| O6 | The deploy pipeline pushes straight to production on every push to `main`; there is no staging site. |

## 9. Needs a decision from the merchant (blocks launch)

1. **Payment**: mobile money, card, or manual (customer pays by transfer after a call). Provider choice decides the adapter to build.
2. **Delivery**: areas, prices, the real cut-off time, and the pickup address and hours.
3. **Bottle, sizes and prices**, and the first real products with real photographs.
4. **Who gets order alerts**, and by which channel (WhatsApp, SMS or email).
5. **Contact details** to show on the site (WhatsApp number, social links).
6. **Business and legal details** for the legal pages.

## 10. Suggested build order

1. **Before any real order**: A1 order alerts, S1 bot protection, J1 and A3 order tracking and customer messaging, O3 legal pages, J3 contact link, C1 budget alert, S5 owner account and live admin walkthrough.
2. **Launch week**: payment adapter (once chosen), real products and photos, A2 bulk import, P1 to P5 titles and sharing previews, O1 and O2 monitoring and backups, O4 domain.
3. **After launch**: A4 and A5 admin extras, O5 automated browser tests, S2 content security policy, C2 video delivery if video grows.
